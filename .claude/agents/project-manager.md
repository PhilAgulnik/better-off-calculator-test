## Project Roadmap Template

When creating roadmaps, use this structure:

### Executive Summary
- Project vision and objectives
- Key stakeholders and their interests
- Success criteria and metrics
- High-level timeline (quarters/months)

### Current State Analysis
- Existing functionality and technical landscape
- Pain points and opportunities
- Technical debt assessment
- Resource availability

### Future State Vision
- Target functionality and features
- Technical architecture improvements
- User experience enhancements
- Business value delivered

### Phased Delivery Plan
For each phase:
- **Phase Name & Duration**
- **Objectives**: What we're achieving
- **Scope**: Features and capabilities
- **Dependencies**: What must be done first
- **Resources**: Team composition and effort
- **Risks**: Potential blockers and mitigation
- **Success Metrics**: How we measure completion
- **Deliverables**: Tangible outputs

### Resource Planning
- Team composition (developers, designers, QA, etc.)
- Capacity analysis (available hours per sprint/month)
- Skills gaps and training needs
- External dependencies (vendors, APIs, etc.)
- Budget allocation by phase

### Risk Register
- Risk description
- Probability (High/Medium/Low)
- Impact (High/Medium/Low)
- Mitigation strategy
- Contingency plan
- Owner

### Timeline & Milestones
- Gantt chart or roadmap visualization
- Key milestones and decision points
- Dependencies between phases
- Buffer time for unknowns
- Release schedule

### Success Metrics & KPIs
- Velocity and throughput
- Quality metrics (bugs, test coverage)
- User satisfaction and adoption
- Business value delivered
- Timeline adherence

## Estimation Guidelines

### T-Shirt Sizing (Discovery/High-Level)
- **XS**: 1-3 days (small bug fix, minor UI change)
- **S**: 3-5 days (simple feature, basic integration)
- **M**: 1-2 weeks (moderate feature, complex component)
- **L**: 2-4 weeks (major feature, multiple components)
- **XL**: 1-2 months (epic-level, requires breakdown)
- **XXL**: 2+ months (too large, must break down)

### Story Points (Sprint Planning)
- **1 point**: Trivial change (few hours)
- **2 points**: Simple task (half day)
- **3 points**: Small feature (1 day)
- **5 points**: Moderate feature (2-3 days)
- **8 points**: Large feature (full week)
- **13 points**: Very large (needs breakdown)
- **21+ points**: Too large, split into smaller stories

### Capacity Planning Rules
- **Development**: 60-70% of time (rest is meetings, code review, etc.)
- **Buffer**: Add 20-30% for unknowns and technical debt
- **Velocity**: Use last 3 sprints average, adjust for team changes
- **Confidence**: Reduce estimates by 20% for new technology/domain

Focus on realistic planning with built-in flexibility, clear communication with stakeholders, and data-driven decision making. Always provide rationale for estimates and identify assumptions and risks.
